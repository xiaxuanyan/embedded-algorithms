# 双缓冲学习笔记

## 1. 学习目标

读完这份笔记，你应该能解释双缓冲为什么需要两块内存，跟踪 `active` 和 `shadow` 的变化，并使用 `DB_Init`、`DB_write` 和 `DB_swap` 发布一帧数据。

## 2. 为什么需要双缓冲？

假设程序要生成一组波形数据，另一个任务要读取这组数据。如果两者使用同一块内存，写入进行到一半时，读者可能同时看到新数据和旧数据。双缓冲准备两块内存：一块供读者读取，另一块供写者准备新数据；准备好后再交换角色。

本例用 `buf0` 和 `buf1` 保存实际数据，用两个指针表示当前角色：

| 名称 | 作用 |
| --- | --- |
| `active` | 指向当前已发布、供读者读取的数据 |
| `shadow` | 指向写者正在准备数据的缓冲区 |
| `widx` | `shadow` 中已写入的元素数量，也是下一次写入的位置 |
| `active_len` | 当前已发布数据的有效元素数量 |
| `swap_cnt` | 成功发布的次数 |

每块数组最多保存 `DB_SIZE`（当前为 16）个 `uint16_t` 元素。两块数组一直在原位置；交换的是指向它们的指针，并不复制整块数据。

## 3. 三个文件各做什么？

- `Double_buffer.h`：定义数据结构、缓冲区大小、函数声明和临界区宏。
- `Double_buffer.c`：实现初始化、写入、切换和读取等操作。
- `main.c`：演示如何生成两帧数据并观察切换前后的结果。

## 4. 按顺序读懂示例

### 第一步：初始化

```c
Doublebuffer_t db;
DB_Init(&db);
```

初始化后，`active` 指向 `buf0`，`shadow` 指向 `buf1`；长度、写入位置和切换次数都是 0，两块数组被清零。此时虽然 `active` 指向 `buf0`，但 `active_len` 为 0，表示还没有有效的已发布数据。

### 第二步：写入并发布第一帧

示例循环调用 `DB_write(&db, i)`，依次将 0～15 写入 `shadow`。每写入一个元素，`widx` 加 1。写满后调用 `DB_swap(&db)`，第一帧被发布。

| 时刻 | active 指向 | shadow 指向 | active_len | widx |
| --- | --- | --- | --- | --- |
| 初始化后 | buf0 | buf1 | 0 | 0 |
| 第一帧写满，尚未发布 | buf0 | buf1 | 0 | 16 |
| 第一帧发布后 | buf1 | buf0 | 16 | 0 |
| 第二帧写入一半 | buf1 | buf0 | 16 | 8 |
| 第二帧发布后 | buf0 | buf1 | 16 | 0 |

### 第三步：准备第二帧

示例先生成三角波数据，并只写入一半。此时还没有调用 `DB_swap`，所以 `active` 仍指向第一帧；`show_frame` 打印的还是 0～15。再写完剩余数据并调用 `DB_swap`，读者才会看到第二帧：

```text
0 2 4 6 8 10 12 14 14 12 10 8 6 4 2 0
```

两次发布成功后，`DB_swap_count(&db)` 返回 2。

## 5. 关键函数

| 函数 | 用法和结果 |
| --- | --- |
| `DB_Init(&db)` | 初始化缓冲区；使用其他函数前先调用 |
| `DB_write(&db, value)` | 将一个元素写入 `shadow`；写入成功返回 `true`，满了返回 `false` |
| `DB_swap(&db)` | 发布已写入的数据并交换角色；没有写入任何元素时返回 `false` |
| `DB_active(&db)` | 返回当前已发布数据的首地址 |
| `DB_active_len(&db)` | 返回当前已发布数据的元素数量 |
| `DB_swap_count(&db)` | 返回成功发布的次数 |

注意：`DB_swap` 只检查是否至少写入了一个元素，**不会检查是否写满 16 个**。因此调用者需要按自己的规则决定何时发布；例如一帧必须是 16 个元素时，应确认写满且每次写入都成功后再切换。

`show_frame` 通过 `DB_active` 取得地址、通过 `DB_active_len` 取得长度，再用下标访问每个元素。它是演示程序里的辅助函数，不是双缓冲模块的公开接口。

## 6. 使用时需要注意的地方

当前示例在单线程中顺序运行，可以直观看到角色切换。在中断、多个线程或 DMA 并发访问时，头文件中的临界区宏默认是空的；`volatile` 也不能代替同步机制。需要根据平台正确处理同步：

1. 保证读取指针和长度时得到一致的一组值，并正确保护共享状态。
2. 保证读者使用旧 `active` 数据期间，写者不会因为后续切换而覆盖那块内存。仅保护 `DB_swap` 的几行代码并不能保证这一点。
3. 多线程需使用符合平台和语言内存模型的同步手段；DMA 还要考虑传输完成和缓存一致性。中断屏蔽方案应保存并恢复原有中断状态。

因此，这个实现适合用来学习基本流程；实际并发移植前，应按读写者的时序设计所有权和同步策略。

`main.c` 中的 Windows 控制台编码设置只是为了正确显示中文，与双缓冲算法无关。

## 7. 自测练习

1. 初始化后马上读取，为什么 `active_len` 是 0？
2. 如果只写 8 个元素就调用 `DB_swap`，函数会返回什么？发布长度是多少？
3. 连续调用 17 次 `DB_write` 且中间不切换，第 17 次会发生什么？
4. 第二帧写到一半时，为什么示例仍能读到第一帧？
5. 如果读者持有旧帧指针很久，写者连续切换并继续写入，旧帧还一定保持不变吗？

参考：第 2 题返回 `true`、长度为 8；第 3 题返回 `false`；第 5 题不一定，需要额外协调缓冲区所有权。
